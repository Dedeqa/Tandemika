# Структуры Go-проектов

## TL;DR
Сначала **стандартные директории** (это про язык: `cmd/`, `internal/`, `pkg/`), потом **философия
раскладки кода внутри** (flat / by-layer / by-feature / hexagonal). Tandemika = **by-feature в
`internal/`** + тонкий `internal/platform/` (ADR-001). Раскладку не делают «на вырост» — дробишь, когда реально разрослось.

## Часть 1. Стандартные директории
| Папка | Что | Особенность |
|---|---|---|
| корень (`go.mod`) | корень модуля | тут же Makefile, docker-compose, README |
| `cmd/<bin>/main.go` | точки входа | **одна папка = один бинарь** (`cmd/api/`, позже `cmd/worker/`) |
| `internal/` | приватный код | **компилятор запрещает** импорт извне модуля — языковая фича |
| `pkg/` | «публичная» библиотека | соглашение для кода «наружу». Спорный — не плодить без нужды |
| `migrations/` | SQL-миграции | ADR-003 |

Ключевое: `internal/` — реальная защита компилятором, поэтому почти весь код там. `pkg/` нужен,
только если осознанно отдаёшь что-то наружу (на pet-проекте — почти никогда).

## Часть 2. Четыре способа раскладки кода

### A. Flat (плоско)
Весь код в 1-2 пакетах в корне. 👍 крошечные CLI/библиотеки/прототипы. 👎 быстро каша.

### B. By-layer (по техническим слоям)
`internal/{handlers,services,repositories,models}` — папки = роли.
👍 интуитивно, легко начать.
👎 одна фича размазана по 4 папкам; пакеты-«боги» (`services` знает про всё); двое дерутся за файлы.

### C. By-feature (по доменным фичам) — **наш выбор**
`internal/{user,auth,schedule}/` — внутри каждой все слои (handler/service/repo).
👍 фича локализована → меньше merge-конфликтов (важно для двоих); чёткие границы; масштаб «модуль за модулем».
👎 иногда дублирование мелких хелперов (лечится `platform/` или `internal/shared/`).

### D. Hexagonal / Clean / DDD
`internal/{domain,usecase,adapters,ports}` — жёсткое разделение домена и инфраструктуры.
👍 максимум тестируемости/изоляции; хорошо для больших команд.
👎 много бойлерплейта (интерфейсы, мапперы) — **оверкилл для pet-проекта** (поэтому отвергли в ADR-001).

## Где сидит Tandemika (ADR-001)
Раскладка **C** + тонкий `internal/platform/` для инфраструктуры:
- фичи (`user`, `auth`) сверху, плумбинг (`config`, `logger`, `postgres`, `redis`, `httpserver`) в `platform/` снизу;
- зависимости текут **только вниз**: фичи знают про platform, platform не знает про фичи;
- глубина каждого модуля живёт в своём пакете (конкуренция в `schedule`, идемпотентность в `tests`).

### Целевое дерево (Модуль 1)
```
cmd/api/main.go
internal/
  user/        handler.go service.go repo.go
  auth/        handler.go service.go token.go middleware.go
  platform/
    config/ logger/ postgres/ redis/ httpserver/
  health/      health.go
migrations/
```

## Главная оговорка
Раскладка — не догма. Начинаешь с минимального C, дробишь пакет, когда разросся. Преждевременные
15 папок «ради архитектуры» = тот же оверинжиниринг, что DDD на пет-проекте.

## Проверь себя
- Чем `internal/` отличается от `pkg/`? → *`internal/` приватность форсит компилятор; `pkg/` — просто соглашение «наружу».*
- Почему by-feature лучше by-layer для двоих? → *фича локализована в одном пакете → меньше конфликтов и пакетов-«богов».*
- Почему отвергли hexagonal/DDD? → *много бойлерплейта, оверкилл для pet-проекта (ADR-001).*
- Что такое platform-пакеты? → *инфраструктурная часть раскладки C; зависимости текут только вниз, к ним.*
- Сколько main.go на бинарь? → *один; `cmd/<bin>/main.go`.*
