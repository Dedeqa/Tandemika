# HTTP-таймауты сервера в Go

## TL;DR
Дефолтный `http.Server` в Go **не ставит таймаутов вообще** (`0` = бесконечно). Это дыра:
медленный/висящий клиент держит горутину и сокет сколько хочет. Таймауты надо задавать руками
на `http.Server`. Роутер (chi) тут ни при чём — он просто `http.Handler`.

## Три таймаута, которые мы используем

### `ReadTimeout` (`http.Server.ReadTimeout`)
- **Что меряет:** время на чтение **всего запроса** (заголовки + тело) от приёма соединения.
- **Зачем:** защита от медленных клиентов. Атака **Slowloris** — слать запрос по байту в секунду,
  держа соединение «полуоткрытым»; сотней таких можно положить сервер без единого полного запроса.
- **При истечении:** соединение рвётся, handler не вызывается.
- **Подвох:** считается на всё тело → большие аплоады (Модуль 3) глобальный `ReadTimeout` будет рубить.
  Тогда — маленький `ReadHeaderTimeout` + контроль тела per-route.
- **Дефолт у нас:** `5s`.

### `WriteTimeout` (`http.Server.WriteTimeout`)
- **Что меряет:** время на **запись ответа** клиенту (примерно от конца чтения заголовков до конца ответа).
- **Зачем:** не дать медленному клиенту / зависшему handler'у бесконечно держать соединение на отдаче.
- **При истечении:** соединение рвётся на середине → клиент получает обрезанный ответ.
- **Подвох:** это дедлайн на **весь** ответ → для streaming/SSE/**WebSocket** (Модуль 5 — чат) его надо
  отключать или выносить такие роуты на отдельный сервер, иначе порвёт долгие соединения.
- **Правило:** `WriteTimeout` ≥ `ReadTimeout`.
- **Дефолт у нас:** `10s`.

### `ShutdownTimeout` (аргумент `srv.Shutdown(ctx)`, НЕ поле сервера)
- **Что меряет:** сколько ждать завершения **уже выполняющихся** запросов после `SIGINT`/`SIGTERM`,
  прежде чем убить сервер принудительно.
- **Как работает graceful shutdown:**
  1. `srv.Shutdown(ctx)` перестаёт принимать новые соединения;
  2. ждёт, пока in-flight запросы доработают — но не дольше `ctx` (= ShutdownTimeout);
  3. не успели → обрыв.
- **Зачем:** при деплое/рестарте не рвать запросы пользователей.
- **Важно:** должен быть **меньше** grace period оркестратора (k8s по умолчанию 30s между SIGTERM и SIGKILL),
  иначе тебя прибьют раньше, чем закроешься.
- **Дефолт у нас:** `10s`.

## Главные грабли (на которые я уже наступил)
1. **`time.Time` vs `time.Duration`.** Таймаут — это ПРОМЕЖУТОК (`5s`), тип `time.Duration`.
   `time.Time` — это МОМЕНТ на календаре. `http.Server.ReadTimeout` имеет тип `time.Duration`.
2. **chi ≠ место для таймаутов.** chi — это `http.Handler`, кладётся в `http.Server{Handler: r}`.
   Таймауты — на `http.Server`.
3. **`chi middleware.Timeout(d)` — это ДРУГОЕ.** Оно ставит дедлайн на `context` запроса (сколько
   работает handler) и возвращает `504`. `Read/WriteTimeout` — про байты по сети. Разные слои, оба нужны.

## Родственники (знать, в каркас можно не тащить)
- **`ReadHeaderTimeout`** — таймаут только на заголовки (полезно, когда тело может быть долгим).
- **`IdleTimeout`** — сколько держать keep-alive соединение МЕЖДУ запросами; без него простаивающие копятся.

## Как это выглядит в коде
```go
srv := &http.Server{
    Addr:         cfg.HTTPAddr,
    Handler:      r,             // chi.Router
    ReadTimeout:  cfg.ReadTimeout,
    WriteTimeout: cfg.WriteTimeout,
}
// ... graceful:
ctx, cancel := context.WithTimeout(context.Background(), cfg.ShutdownTimeout)
defer cancel()
srv.Shutdown(ctx)
```

## Проверь себя
- Чем `ReadTimeout` отличается от `chi middleware.Timeout`? → *слой соединения (байты) vs дедлайн handler'а (context, 504).*
- Почему `WriteTimeout` нельзя оставлять на WebSocket-роутах? → *рвёт долгоживущие соединения по дедлайну ответа.*
- Почему `ShutdownTimeout` < grace period оркестратора? → *иначе SIGKILL прилетит раньше корректного закрытия.*
- Какой тип у таймаута и почему не `time.Time`? → *`time.Duration` — это длительность, `time.Time` — момент.*
