# Логирование в Go: slog vs zap

## TL;DR
Для обычного web-сервиса бери **`log/slog`** (stdlib с Go 1.21): ноль зависимостей, структурное
логирование, идиоматично. **zap** оправдан только когда логирование стало узким местом по перформансу
или нужны его зрелые фишки. И ты не запираешься: `slog` — это интерфейс, под него можно подложить zap.

## Сравнение

| | `log/slog` (stdlib) | `go.uber.org/zap` |
|---|---|---|
| Зависимости | нет | внешняя |
| Структурные логи | да | да |
| Перформанс | хороший | очень высокий (zero-alloc в типизированном API) |
| Зрелость | молодая, но стандарт | многолетняя, богатая экосистема |
| Сигнал в резюме | «современный stdlib» | «классика, но slog новее» |

## Когда брать zap
1. **Горячий путь с огромным объёмом логов** (десятки-сотни тысяч строк/сек), где аллокации на каждую
   запись бьют по latency/GC. zap без `Sugar` (`zap.String`, `zap.Int`, …) почти не аллоцирует.
2. **Нужны зрелые фишки из коробки:** сэмплинг логов, готовые энкодеры, тонкая настройка.
3. **В кодовой базе/команде уже zap** — единообразие важнее.

## Когда хватает slog (наш случай)
- Обычный web-сервис, умеренный объём логов.
- Хочешь ноль зависимостей и идиоматичный современный Go.
- Чистый API: `slog.Logger` + сменный `slog.Handler` (text для dev / json для prod).

## Главное: slog — это интерфейс, ты не в vendor-lock
`slog` задал стандартный `slog.Handler`. Если упрёшься в перформанс — подложишь zap ПОД slog через
`go.uber.org/zap/exp/zapslog`, **не меняя мест вызова**:
```go
// весь код пишет в slog.Logger; движок меняется в одном месте (main)
logger := slog.New(zapslog.NewHandler(zapCore)) // zap внутри, slog снаружи
```
Пишешь против `slog` сейчас → при необходимости меняешь движок потом.

## Решение для Tandemika
`slog` с двумя хендлерами по `LOG_FORMAT`:
- `text` (`slog.NewTextHandler`) — локалка, читаемо глазами;
- `json` (`slog.NewJSONHandler`) — prod, грепается/собирается;
- уровень из `LOG_LEVEL` → `slog.Level` (через `HandlerOptions.Level`).

zap прибережём на случай, если **профайлер** покажет, что логирование — бутылочное горлышко
(на pet-проекте почти наверняка не покажет).

## Проверь себя
- Когда zap реально нужен вместо slog? → *горячий путь с огромным объёмом логов / нужны его фишки / уже в кодовой базе.*
- Как использовать zap, но не переписывать вызовы? → *`zapslog.NewHandler` как `slog.Handler` под `slog.New`.*
- Чем `slog.Sugar`-аналог в zap плох на горячем пути? → *аллокации; типизированный API zap zero-alloc.*
- Почему slog — хороший сигнал в резюме сейчас? → *показывает знание современного stdlib (Go 1.21+).*
