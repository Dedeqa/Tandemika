> Смена статуса — отдельной строкой `- **Обновление YYYY-MM-DD:** ...`, а не правкой текста.
> Нумерация сквозная. Перед присвоением номера **проверь последний ADR здесь**, чтобы не было коллизии.

## ADR-001: Структура проекта — feature-based internal
- **Дата:** 2026-06-06
- **Автор:** @fedos
- **Статус:** Принято
- **Контекст:** Нужен предсказуемый layout, который масштабируется по модулям (core → schedule → … → chat) и понятен двум разработчикам без долгого онбординга.
- **Решение:** Стандартный Go-layout. Точки входа в `cmd/<bin>/`. Бизнес-код в `internal/`, сгруппированный **по фиче**: `internal/<фича>/{handler,service,repo}.go` (например `internal/user`, `internal/auth`). Общая инфраструктура — в `internal/platform/` (config, db, redis, httpserver) или аналогичных общих пакетах. Каждая фича — отдельный пакет, чтобы двое реже трогали одни файлы.
- **Альтернативы:** DDD-lite слои (`domain/usecase/repository/transport`) — отвергнуто как избыточный бойлерплейт для pet-проекта (риск переусложнения без пользы для резюме).
- **Последствия:** Меньше слоёв и церемоний; при росте фичи возможна внутренняя пересборка пакета. Граница «фича = пакет» снижает merge-конфликты между двумя разработчиками.

## ADR-002: HTTP-роутер — chi
- **Дата:** 2026-06-06
- **Автор:** @fedos
- **Статус:** Принято
- **Контекст:** Нужен роутинг + middleware (auth, logging, recovery) без тяжёлого фреймворка, с понятной интеграцией поверх stdlib.
- **Решение:** `go-chi/chi`. Лёгкий, идиоматичный, совместим с `net/http` (handlers/middleware — стандартные сигнатуры). Демонстрирует понимание stdlib в резюме.
- **Альтернативы:** std `net/http` (1.22+) — отвергнуто: пришлось бы писать весь middleware-слой вручную, замедляет старт. `echo` — отвергнуто: больше «магии» и vendor-lock, меньше демонстрации базового понимания.
- **Последствия:** Одна внешняя зависимость; middleware пишем/собираем сами, но на знакомых интерфейсах `http.Handler`.

## ADR-003: Инструмент миграций — golang-migrate с timestamp-неймингом
- **Дата:** 2026-06-06
- **Автор:** @fedos
- **Статус:** Принято
- **Контекст:** Нужны версионируемые SQL-миграции (up/down), запускаемые локально и в CI. Двое работают параллельно в feature-ветках → последовательная нумерация (`000001`, `000002`) гарантированно даёт коллизии версий при merge.
- **Решение:** `golang-migrate/migrate`. Файлы именуются по **timestamp**: `YYYYMMDDHHMMSS_<описание>.up.sql` / `.down.sql` (например `20260606153000_create_users.up.sql`). Каждая миграция — пара up/down. Запуск через Makefile-таргет и в CI.
- **Альтернативы:** goose — отвергнуто: преимущества (embed, Go-миграции) для текущего scope не нужны; golang-migrate узнаваемее в резюме. Последовательная нумерация в golang-migrate — отвергнута из-за коллизий у двоих.
- **Последствия:** Каждое изменение схемы = новая пара миграций (продакшн-привычка). Timestamp-нейминг практически исключает коллизии версий между ветками; при правке одной таблицы двумя людьми возможны логические (не номерные) конфликты — координируем через [[03-Log]].

## ADR-004: JWT-стратегия — access + refresh с ротацией и отзывом через Redis
- **Дата:** 2026-06-06
- **Автор:** @fedos
- **Статус:** Принято
- **Контекст:** Аутентификация Модуля 1. Нужны logout, отзыв сессий и защита от переиспользования украденного refresh — голый stateless-JWT этого не даёт. Заодно это осмысленно задействует Redis (глубина для резюме).
- **Решение:**
  - **Access-токен:** JWT (HS256 на старте), короткий TTL (~15 мин), несёт `sub`, `role`, `jti`, `exp`. Проверяется stateless в middleware.
  - **Refresh-токен:** длинный TTL (~30 дней), хранится на сервере. При обновлении — **ротация** (старый инвалидируется, выдаётся новый); повторное использование старого refresh → отзыв всей цепочки (детект кражи).
  - **Отзыв:** состояние refresh/jti в **Redis** с TTL = времени жизни токена (whitelist активных refresh + blacklist отозванных access по jti при logout).
- **Альтернативы:** Только access-JWT без refresh/отзыва — отвергнуто: нет logout, слабее для резюме. Сессии в БД без JWT — отвергнуто: теряем демонстрацию JWT и нагружаем Postgres на каждом запросе.
- **Последствия:** Redis становится обязательной зависимостью аутентификации. Чуть больше кода (ротация, детект reuse), но это и есть целевая нетривиальная логика модуля. Секрет подписи — через конфиг/ENV, не в репозитории.
